# Multimodal Drawing Review System

https://github.com/user-attachments/assets/a815408f-6fef-4315-a157-25a5fc8508ed

When someone marks up a technical drawing and sends it back to be corrected, a
human then has to check, by eye, whether every correction was actually made.
This tool screens that revision: given the marked-up file and the corrected
file, it reports possible misses, changes needing review, verified label
corrections, and changes outside the marked targets.

It runs entirely on the local machine. No file is uploaded anywhere.

*Everything in the animation is synthetic — the drawings are generated by a
script in this repository and the findings come from running the real
comparison over them.*

---

## Why this is harder than it sounds

The obvious implementation — overlay the two files and highlight the differences
— fails on real documents for four separate reasons, and each one drove a design
decision worth explaining.

### 1. The pages stop lining up

Compare page 1 to page 1 and page 2 to page 2, and everything works until
someone inserts or drops a sheet. Then every subsequent
pairing is off by one and the tool confidently compares unrelated drawings. This
is the failure mode that makes a comparison tool worse than useless: it produces
a full report, and the report is nonsense.

Each page is reduced to a 32×32 fingerprint rendered at ~36 DPI, and the two
documents are aligned with **Needleman–Wunsch** — global sequence alignment from
bioinformatics. The fit is exact rather than decorative: the matching must be
**monotonic** (page order is preserved on both sides) while tolerating
insertions and deletions on either, which is precisely the problem sequence
alignment solves. Pages whose displayed orientation differs are scored `-1e9`,
so a portrait page can never pair with a landscape one however similar the ink.

Unmatched pages are *reported* as inserted or dropped rather than silently
forced onto a partner. You can watch it happen:

```bash
python examples/make_sample_drawings.py --scenario inserted
python comparator.py examples/inserted_redlined.pdf examples/inserted_revised.pdf -o report
```

Three marked-up sheets against four revised ones with the new sheet in the
middle: the three real pairs still line up, and the inserted sheet is reported
separately rather than shifting everything after it.

### 2. A pixel diff is blind to the most important edit

Changing a label from `W200X52` to `W310X52` places nearly identical ink in an
identical position. The diff registers nothing — and would report the
instruction as ignored when it was in fact carried out. This is not an edge
case; it is one of the most common corrections made.

Two verification tiers read the text at the target instead of looking at pixels:
Tesseract OCR first, then a local vision model via Ollama for what OCR cannot
resolve. OCR on thin technical lettering fails in *predictable* ways, so
matching folds the characters Tesseract routinely confuses — `B`↔`8`, `S`↔`5`,
`I`/`L`↔`1`, `G`↔`6`, `Z`↔`2`, `D`/`Q`/`O`↔`0` — on both sides of the
comparison, and tolerates a bounded number of stray characters between matched
ones. Short labels must match a whole recognised word so `B3` cannot falsely
match `SB3`.

### 3. The two kinds of error are not equally expensive

This is the decision I would defend hardest. Wrongly reporting *"this was
handled"* sends an uncorrected drawing onward to be issued. Wrongly reporting
*"possible miss"* costs a reviewer a few seconds. Those costs differ by orders
of magnitude, so the system is deliberately asymmetric rather than
accuracy-maximising:

> The green **Addressed (verified)** verdict is issued only when the instructed
> value is actually *read back* at the target. Pixel activity alone is never
> sufficient — it reports **to verify** instead.

The same asymmetry drove a counter-intuitive default. Suppressing *local* shifts
cancels a lot of re-plot noise, and switching it on measurably reduces false
positives. It is off (`suppress_local_shifts_always = False`) because on
drawings with repeated content — several identical rooms relabelled the same way
— it matches a nearby duplicate and erases a **real** change. Trading a real
detection for a quieter report is the wrong trade when the report's whole
purpose is catching what a human missed.

### 4. Resolution should not change the answer

The diff's grain is defined in **points, not pixels**, so rendering at higher
resolution does not multiply false positives — a property that matters on large
sheets which produce very large rasters. Render DPI is chosen from the drawing's
own text size, targeting roughly 30-pixel-tall labels, clamped to 200–500.

Repeated content like title blocks and revision stamps is dropped by
**fingerprinting each region's image and clustering by content across sheets**,
with a conservative position-based fallback. Position-only detection lets boilerplate through on exactly
the sheets where it shifts slightly, which is where it floods the report.

## Try it in three commands

Use Python 3.9 or newer in a virtual environment (`python3 -m venv .venv`,
then `source .venv/bin/activate` on macOS/Linux or `.venv\Scripts\activate` on
Windows).

```bash
pip install -r requirements.txt
python examples/make_sample_drawings.py
python comparator.py examples/basic_redlined.pdf examples/basic_revised.pdf -o report
```

The generated sample requests two changes; the revision applies one, ignores the
other, and adds something nobody asked for:

```
==================  SUMMARY  ==================
  Possible misses (review):   2
  Unexpected changes:         1
  To verify (coordination):   0
  Addressed (verified):       0
==============================================
```

The unrequested addition is caught. Both instructions land in *possible misses*
rather than one being confirmed — because the change that *was* applied is an
in-place text swap the pixel diff cannot see. That is section 2 above,
reproduced deliberately in the sample so the limitation is visible rather than
hidden. Resolving it is what the `--ocr` tier is for; that path needs the
Tesseract binary, which is not bundled:

```bash
winget install UB-Mannheim.TesseractOCR    # Windows; requires admin
# macOS: brew install tesseract
# Debian/Ubuntu: sudo apt install tesseract-ocr
python comparator.py examples/basic_redlined.pdf examples/basic_revised.pdf -o report --ocr
```

Open `report/summary.html` for before/after crops of every finding. A browser UI
is available with `streamlit run app.py`. The CLI leaves OCR off unless requested;
the UI enables OCR initially when Tesseract is available. Ollama is always opt-in.

With OCR, a newly read alternative label in the same family (asked for `L5`,
changed `L3` to `L4`) is **Changed (other)** under *To verify*. Pixel activity
alone is **Change at target (review)**. A missing label is a possible miss;
only a confirmed requested value earns **Addressed (verified)**. Partial
instructions, removed placeholders, and hexnote numbers found elsewhere on the
sheet stay in review. Short labels retain stricter verification guards.

### The other scenarios

`python examples/make_sample_drawings.py --scenario <name>` builds a pair that
exercises one specific behaviour. These are the observed results of running the
comparator over each:

| Scenario | What it exercises | Result |
|---|---|---|
| `basic` | in-place swap, missed instruction, unrequested change | 2 misses, 1 unexpected |
| `inserted` | a sheet inserted into the revision | 3 misses, **1 extra page** |
| `dropped` | a sheet missing from the revision | 2 misses, **1 extra page** |
| `flattened` | markups baked in as red ink, no annotations | 1 to verify |
| `rotated` | page stored portrait, displayed landscape | 1 miss, no crash |
| `boilerplate` | same title-block change on 4 sheets | 4 misses, **0 unexpected** |
| `copyref` | "copy the comments from sheet X" | 2 to verify |
| `replot` | revision re-plotted at a large offset | 2 unexpected, 1 to verify |

`inserted` and `boilerplate` are the two worth running: they are the cases where
a naive implementation produces a confidently wrong report. `boilerplate` puts
the identical title-block change on four sheets and returns **zero** unexpected
findings — that is the content-fingerprint suppression doing its job.

`replot` is the honest one. A heavily re-plotted sheet costs false positives,
which is why every finding ships with before/after crops rather than asking
anyone to trust a count.

## Tests

```bash
pip install pytest
python -m pytest -q
```

Coverage includes all eight generated scenarios, CLI report exports, browser
results, real Tesseract read-back when installed, and the optional model's
verdict policy with synthetic model responses. The alignment tests assert *properties*
that must hold for any input — pairings never cross, every page index is
accounted for exactly once — rather than checking fixed examples, so a
regression in the aligner cannot slip through on an untested shape. All fixtures
are synthetic; no drawing is required to run them.

## Scope and limitations

- **This is a screening pass, not an adjudicator.** It tells a reviewer where to
  look. Every finding ships with before/after crops because a human confirms.
- **Without `--ocr` or `--vlm`, in-place text edits cannot be confirmed** and may
  surface as possible misses. The CLI leaves both tiers off by default.
- **The vision tier needs a real GPU.** On CPU it costs minutes per call, so it
  is opt-in and runs only on what OCR could not resolve.
- **Heavily re-plotted sheets produce false positives.** Below a
  post-registration similarity of 0.30, per-region flags are suppressed in
  favour of a single page-level "review manually" notice; above it, a large
  re-plot still costs noise.
- **Calibrated against one firm's drawing conventions.** Markup extraction
  assumes Acrobat annotations, with a red-ink fallback for flattened markups.
  Other conventions will need the thresholds in `redlinecheck/config.py`
  retuned; they are centralised and documented for that reason.
- **The OCR tier verifies red FreeText spec comments**, not every markup type.
- Scanned or image-only files degrade to pixel-only comparison.
- Repeated genuine edits across sheets can resemble boilerplate and be
  suppressed. A fingerprint mismatch or a heavily changed sparse sheet can
  require whole-sheet review instead of region-level findings.
- A project run matches files one-to-one. Combine a revision split across
  several PDFs into one PDF before comparing it against a single marked-up file.
- Tested on Windows and macOS. Nothing in it is Windows-specific apart from the optional
  click-through installer under `installer/`.

## Layout

```
redlinecheck/     the engine: prematch, extract, align, diff, classify, report
comparator.py     single-pair command line entry point
app.py            browser UI (Streamlit)
tools/            whole-project runner and dev utilities
examples/         synthetic drawing generators (8 scenarios)
tests/            synthetic unit and integration regression tests
```
